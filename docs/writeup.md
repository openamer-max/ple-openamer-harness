A failure analysis of the 29 public dev tasks of Physical-Engineering's Last Exam,
recomputed from the reference run shipped in the public submission template
(Pi 1.1.0 + Claude Opus 5.5). Every number below is regenerated by the scripts in the
repository from `artifacts/manifest.json` and `artifacts/*/trajectory.json`. We did not
run the dev set ourselves — that requires gated dataset access, which we did not obtain
before writing this. We therefore claim no score of our own and mark every prediction
as a prediction.

**Headline finding.** The four zero-scoring tasks are not one failure but two disjoint
ones. **Two never wrote a deliverable at all** (73 and 22 steps, zero files collected).
**Two wrote on step 3 and step 4** of a 124- and 160-step budget and still scored
0.000 — their artifact was structurally invalid. Absent deliverable and invalid
deliverable need different harness gates, and conflating them is why "just write
earlier" does not recover the score.

## 2. Insight: two failure classes (criterion 1)

**Class A — no deliverable (2 tasks, both 0.000).**
`foundation-strategy` (73 steps) built an optimisation model and spent the run tuning
parameters; it never wrote `output/submission.zip` and ended mid-patch.
`solar-witness-test-package` (22 steps) ended mid-`curl`. The task prompt states the
requirement verbatim: *"a run that exhausts its step or token budget with no file scores
0."* Every individual step was plausible engineering. The failure is budget allocation,
not knowledge.

The official kit reaches the same conclusion independently:
`foundation-strategy: nothing this task's grader reads: no file under files/`.

**Class B — invalid deliverable (2 tasks, both 0.000).**
`data-hall-mep-routing` (first file at step 4 of 124) and
`data-hall-mep-routing-offset` (step 3 of 160) required an **IFC4 model generated by
script** from **seven PNG drawing sheets and nothing else**. The agent delivered a
758-line `solution.py` writing an IFC file. A collected file plus reward 0.000 means the
grader rejected the artifact. 120 further steps did not repair it, because nothing in
the loop tested validity.

**Failed ideas.** We tried, and abandoned, two interpretations of our own:
(a) that late submission explains the zeros — it does not, the two perfect scores sit at
step 6 of 39 (15 %) and step 58 of 69 (84 %);
(b) that the failures are domain-knowledge gaps — section 3 shows the harness solving a
cable-sizing task at 0.907 with textbook method.

**Taxonomy.** (1) no deliverable (2/29); (2) invalid artifact (2/29); (3) drawing
comprehension from raster sheets alone (≥4/29, including both MEP tasks); (4) code-clause
selection and (5) unit handling — both **hypotheses, not findings**: the public artifacts
carry no grader feedback per criterion, and keyword counts measure mentions, not errors.

**Three ablations, stated as predictions, not results.**

| # | Harness change | Predicted effect | Measurement |
|---|---|---|---|
| A1 | First-version mandate: a schema-complete file at the deliverable path by 25 % of budget | both class-A tasks leave 0.000; empty `files/` goes 2/29 → 0/29 | per-task reward; count of empty `files/` |
| A2 | Self-validation gate: parse and check the artifact against the stated schema before each submission attempt | both class-B tasks leave 0.000 | per-task reward; count of "file present, reward 0" |
| A3 | Discovery time-box: cap service/document exploration at 25 % of budget, then force a scaffold | `solar-witness-test-package` runs past step 22 and delivers | steps to termination; reward |

## 3. Engineering reasoning on a concrete task (criterion 2)

`lv-cable-sizing` scored **0.907** in 76 steps. Its trajectory is close to how a licensed
electrical engineer actually works, and worth reading step by step.

*Inventory.* Step 2 lists the project and counts files; step 3 reads `task.md`; step 4
checks which tools exist (`pdftotext`, `openpyxl`, `ezdxf`) before committing to an
approach.

*Governing documents, including revision control.* Step 6 reads the electrical design
standard **rev4 and rev2, the latter flagged SUPERSEDED**. Checking which revision
governs is the single most consequential habit in code-based engineering, and the agent
did it unprompted. Steps 18–29 then query the UFC library for voltage drop (§3-2.7),
load analysis and spare capacity (§3-2.3), fire-pump load, aluminium versus copper
conductors, 60 °C versus 75 °C terminations, tray fill, and equipment grounding
(§250.122).

*Vendor data and CAD.* Steps 8–11 read manufacturer datasheets and a price list, and
parse the panel schedules from spreadsheets. Steps 12–17 parse the DXF drawings
(one-line diagram, level plans, riser, duct bank) with `ezdxf` and dump entities — the
agent reads CAD, not a rendering of it.

*Calculation tooling.* Steps 30–34 build a small toolchain: `lengths.py` extracts circuit
lengths from the DXF entities, `cable.py` holds ampacity tables, `env.py` derives the
thermal environment, `nm.py` implements **Neher–McGrath** conductor temperature rise, and
`db1.py` searches the admissible design space.

Where it held up: method, revision awareness, unit discipline, and tool-building.
Where the same harness fell short elsewhere: it never guaranteed an artifact. The gap
between 0.907 and 0.000 is not engineering skill.

**The class-A failure is a different animal.** `solar-witness-test-package` has inputs
spread across **local services**: a Wiki.js instance answering GraphQL on port 5016, an
OpenProject API on 5009, a document store, plus PDFs and DOCX. The agent spent steps
8–22 on `/etc/hosts`, a port sweep 5007–12345, `ps aux`, `/opt/openproject`,
`/opt/wikijs`, then dumped 53 wiki pages and grepped correspondence letters (an AML
escalation, a backlog review directive) — and the run ended before any deliverable
existed. The dominant cost of information-integration tasks is **discovery, not
reasoning**, and discovery cost is unbounded unless the harness bounds it. That is what
ablation A3 addresses.

## 4. Cross-model generalizability (criterion 3)

We cannot yet report our own cross-model runs, because we could not access the dev set.
What the public record does show is the spread on the official leaderboard (their
harnesses, not ours): GLM-5.2 **26**, DeepSeek-V4.1-Flash 17, Qwen3-Coder-480B 6.1,
Kimi-K2-Thinking 5.7, Gemma-4-26B-A4B 5.2, MiniMax-M2 4.8, gpt-oss-120b 3.8,
Llama-4-Maverick 0.7 — against 49.1 for the Claude Opus 5.5 reference run.

Two things follow. First, the model spread (0.7 → 26) dwarfs anything a harness tweak
buys on a single task, so a harness paper must argue mechanism, not anecdotes. Second,
the two classes we identify are **allocation phenomena, not capability phenomena**: a
model that never materialises a file cannot be rescued by being smarter. That predicts
A1 and A3 help every model family and A2 helps only models whose artifacts are
near-valid — but this is a prediction we have not measured, and we label it as such.

## 5. Efficiency and scaling (criterion 4)

Score against tool calls (figure 2) has a **negative** slope: r = −0.30 over 29 tasks.
Median spend is 85 tool calls. The two perfect scores used 37 and 76 calls; the four
zeros used 23, 78, 122 and 158. Above 120 calls (six tasks) the best score is 0.461 —
`cooling-water-flush-plan` — and **none reaches 0.5**; two of those six are zero.

**Headroom.** If the four zeros merely reached the median of the 25 non-zero tasks
(0.537), the mean would rise from 0.491 to **0.565** — a **15 % relative gain**. That is
the size of the prize for fixing allocation rather than capability, and it is achievable
with the three gates above at zero additional inference cost.

## 7. Limitations

1. **One model, one run.** All analysis is Claude Opus 5.5 in a single sample submission.
2. **n = 29, ten examined in depth.** Effect sizes on the other 19 are untested.
3. **No own dev runs.** Every ablation prediction comes from mechanism, not measurement.
4. **No self-judged scores.** We used the organisers' published rewards, not a local judge.
5. **Attribution limits.** Classes 4 and 5 cannot be proven from the public artifacts.
